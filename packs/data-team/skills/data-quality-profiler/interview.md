# 操作实录: 数据库数据质量体检（CRM 分析前置）

> 访谈方式：聊法一（回忆上次真实流程）+ 三轮方案重构（人工流程→skill 流程 v3→v4 定稿）。
> 数据不进会话：全程未接触真实连接信息、真实库表数据；样本为流程级复述。

## 任务动机

痛点: 数据分析团队做任何分析前，第一步必须对数据库数据质量有清晰了解；人工做要写几十段统计 SQL、逐表算空值率、排版多份文档，机械劳动量大、易漏表
频率: 每个 CRM 分析项目启动时一次
单次耗时: 人工数天（写 SQL + 跑 + 整理文档）
范围边界: 只读体检，绝不动数据；产出给数据分析师看的四件套（报告/数据字典/体检明细/业务统计）

## 流程实录

### 步骤1 环境摸底

数据: 分析师口头提供：数据库类型（MySQL/PostgreSQL，直接问、只生成对应一版方言 SQL）；执行模式（平台有连库 agent → 模式 I 直连 / 无 → 模式 II 手工接力）；模式 II 下再问查询入口（自有 SQL 客户端 / 网页查询界面）
决策: 凭据零接触——模式 I 凭据配在平台连接器侧，模式 II 分析师用自己的客户端；能力全程不问、不收、不复述连接信息
人工闸门: 分析师自查平台是否有连库能力（不知道就教 30 秒自查法）
交付工件: 连接与执行指引（按三问答案定制）

### 步骤2 全库普查

数据: 一段普查 SQL（按库类型对应方言）：全部表名 + 行数 + 字段数 + 表注释；从 information_schema 生成，不依赖客户端导出功能
决策: 空表/近空表剔除，缩小后续范围；几十张表规模一次贴回可行，不分批
人工闸门: 无（机械执行）
交付工件: 全表清单（含空表标记）

### 步骤3 细看名单确认

数据: 按行数量级 + 表名/注释语义推测业务表 vs 日志/配置/临时表
决策: 能力先给"建议细看名单 + 理由"，不替分析师拍板
人工闸门: ① 分析师增删定稿细看名单
交付工件: 定稿细看名单

### 步骤4 数据字典 + 五维技术体检

数据: 对定稿表批量生成体检 SQL 包——结构 SQL（字段/类型/注释→数据字典底稿）；完整性（每字段空值率，一段 SQL 出全表所有字段）；唯一性（候选键重复率）；有效性（按类型套规则：邮箱/手机/日期/枚举值域）；及时性（最新记录距今、按年分布）
决策: 采用 DAMA 经典维度为骨架（完整性/唯一性/有效性/一致性/及时性；准确性由步骤6外部核对兜底）；大表（如数千万行明细表）改抽样统计并注明"抽样估值"；无注释拼音缩写字段（如 hybj/spmc）标"语义不明"列入待确认清单，不瞎猜
人工闸门: 语义不明字段由分析师去问业务方
交付工件: 数据字典底稿 + 各表红黄绿灯体检明细

### 步骤5 表关系推导

数据: 三样证据——已声明外键（如有）；字段命名规律（order.member_id → member.id）；数据探针 SQL（order.member_id 在 member.id 的命中率，98% 坐实 / 3% 证伪）
决策: 现实中 CRM 库常无外键，关系藏在命名与业务逻辑里；跳过这步直接统计，JOIN 错则报表全错
人工闸门: ② 分析师对"推测关系图"逐条拍板/纠正，定稿关系图
交付工件: 定稿表关系图（后续所有统计 JOIN 的地基；步骤4一致性检查也建立在此图上——孤儿订单、无订单会员等）

### 步骤6 业务统计（CRM 双轴模板）

数据: CRM 通用模板草稿——A 会员域（总量/按年新增/状态分布/有无消费分布）；B 交易域（总量/GMV/客单价/按年/渠道轴/会员轴：会员单 vs 游客单/双轴交叉/近24月趋势）；C 明细域（每单几件/退款占比）；D 交叉一致性（订单总额 vs 明细总额/孤儿数据）；+ 会员订单匹配率（会员体系打通健康度线索）
决策: 模板先行 + 分析师确认定稿，不替分析师决定统计口径；所有数字标注"建议核对来源"（财务报表/后台截图/第三方平台），必须可被证伪
人工闸门: ③ 分析师对统计口径增删改定稿；跑出的数字由分析师拿去和客户手头报表核对（对不上即质量问题线索）
交付工件: 定稿统计口径 + 业务统计结果 + 待核对清单

### 步骤7 四件套产出

数据: 汇总前六步全部结果
决策: 四个独立 Markdown 文件（不合一份）；体检发现每条带"所以呢"（如"37% 会员未绑手机 → 短信渠道对该部分不可达"）
人工闸门: 无（能力直接产出）
交付工件: ① 整体数据质量分析报告（红黄绿总览+风险清单+定稿关系图）② 数据字典文档 ③ 各表体检明细（五维度打分）④ 业务统计结果

## 不做哪些

- 绝不修改/清理/删除任何数据（只读体检，写操作一律拒绝）
- 绝不询问、接收、复述、存储数据库连接信息（地址/账号/密码）
- 不替分析师拍板：细看名单、表关系、统计口径三处均由人工闸门定稿
- 不依赖特定 SQL 客户端的导出功能（数据字典由能力自带 SQL 生成）
- 不做数据修复建议的具体执行（只出风险清单与建议方向）

## 依赖的外部资源

- 数据库本身（MySQL / PostgreSQL），经模式 I（平台连库 agent/连接器）或模式 II（分析师手工接力）访问
- 模式 I 的平台连接器：凭据配置在平台侧，能力只发 SQL
- 客户侧核对数据源：财务报表 / 业务后台截图 / 第三方平台数据（步骤6外部核对用）
- 无前置能力 capId 依赖
